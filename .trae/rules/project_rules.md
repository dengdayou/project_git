# 个人规则：数字员工自动调度与6A+1工作流执行

> 版本：v3.0 | 日期：2026-04-07 | 更新内容：**集成Superpowers理念，引入TDD、子代理开发、系统化调试、任务拆分、代码审查等机制**

## 规则概述

本规则定义了在Trae中自动选择合适的数字员工执行任务，并严格按照 **6A+1 + Superpowers 增强工作流** 执行的规范。

本版本深度融合 **Superpowers 核心理念**，将 AI 编程助手的最佳实践融入数字员工工作流，让数字员工从"任务执行者"进化为**结构化开发者**。

---

## Superpowers 核心原则（四原则）

| 原则 | 说明 | 在数字员工中的体现 |
|------|------|-------------------|
| **测试驱动开发 (TDD)** | 永远先写测试，再写实现 | 所有开发任务必须遵循 RED→GREEN→REFACTOR 循环 |
| **系统性优于临时方案** | 遵循既定流程，不靠猜测 | 强制执行完整工作流，禁止跳过关键步骤 |
| **复杂性降低** | 简化是首要目标 | YAGNI原则：只做当前需要的，不过度设计 |
| **证据优于声明** | 验证后才算完成 | 测试通过 + 代码审查通过 = 任务完成 |

### 各技能详细说明

#### 1. brainstorming（需求澄清与设计探索）
**触发时机**：创建新功能、修改行为、需求不明确时

**工作流程**：
1. 探索用户意图（5W1H分析）
2. 澄清需求细节（提问式澄清）
3. 讨论设计方案（多方案对比）
4. 提出选项并给出推荐
5. 确定最佳方案
6. 输出设计文档

**输出物**：
- 需求澄清记录
- 设计方案文档（含决策理由）

**示例触发**：
```
用户："我想给博客加一个标签云功能"

AI（自动触发brainstorming）：
1. 标签云的展示样式？（列表/权重图/热力图）
2. 是否需要按文章数量排序？
3. 筛选后页面如何变化？
4. 数据来源是什么？

→ 输出设计方案 → 用户确认
```

#### 2. writing-plans（任务拆解与实施计划）
**触发时机**：设计确认后、开始编码前

**拆解原则**：
- 每个任务 **2-5 分钟**可完成
- 任务之间**依赖关系明确**
- 包含**精确的文件路径**
- 包含**验证步骤**

**计划模板**：
```markdown
## 实施计划：[功能名称]

### 任务列表

#### Task 1: [任务名] (~3min)
- **文件**: `src/components/xxx.ts`
- **改动**: 新增组件骨架
- **验收**: 组件可渲染无报错

#### Task 2: [任务名] (~5min)
- **文件**: `src/stores/xxx.ts`, `src/utils/xxx.ts`
- **改动**: 实现数据逻辑
- **验收**: 单元测试通过

...
```

#### 3. test-driven-development（测试驱动开发 TDD）
**强制执行**：所有编码任务必须遵循 TDD 循环

**TDD 三步循环**：
```
┌─────────────────────────────────────────┐
│           TDD 循环                        │
├─────────────────────────────────────────┤
│                                         │
│   ┌───────┐    ┌───────┐    ┌───────┐  │
│   │  RED  │ →  │ GREEN │ → │REFACTOR│  │
│   │ 写测试 │    │写实现  │    │ 重构  │  │
│   │(失败) │    │(通过) │    │(优化) │  │
│   └───────┘    └───────┘    └───────┘  │
│                                         │
└─────────────────────────────────────────┘
```

**TDD 执行规范**：
1. **RED 阶段**：先写失败的测试用例
   - 测试描述清晰表达预期行为
   - 测试必须能运行但失败
   
2. **GREEN 阶段**：写最少代码让测试通过
   - 不追求完美，只求通过
   - 允许"丑陋"的实现
   
3. **REFACTOR 阶段**：优化代码质量
   - 保持测试通过
   - 改善命名、结构、消除重复

**违反处理**：
- 若发现先写了业务代码而非测试 → **停止当前任务**
- 删除已写的业务代码
- 回到 RED 阶段重新开始

#### 4. systematic-debugging（系统化调试 4步法）
**触发时机**：遇到 Bug、测试失败、意外行为时

**调试四步法**：

```
Step 1: 重现问题 (Reproduce)
├── 明确问题的具体表现
├── 记录复现步骤
└── 确认问题可稳定复现

Step 2: 收集信息 (Gather Info)
├── 查看错误日志/堆栈信息
├── 检查相关代码变更
└── 收集环境信息

Step 3: 分析根因 (Analyze Root Cause)
├── 提出假设（可能原因列表）
├── 逐个验证假设
└── 定位根本原因

Step 4: 修复验证 (Fix & Verify)
├── 实施最小化修复
├── 编写回归测试
└── 验证修复有效且无副作用
```

**调试禁令**：
- ❌ 禁止随机尝试修改代码
- ❌ 禁止跳过分析直接修复
- ❌ 禁止"可能修好了就不管了"
- ✅ 必须找到根因
- ✅ 必须有回归测试覆盖

#### 5. subagent-driven-development（子代理驱动开发）
**触发时机**：复杂任务、多模块并行开发时

**子代理调度机制**：
```
主代理（协调者）
    │
    ├── 子代理 A: Task 1（独立任务）
    │   └── 执行 TDD 循环 → 完成后自审
    │
    ├── 子代理 B: Task 2（独立任务）
    │   └── 执行 TDD 循环 → 完成后自审
    │
    └── 子代理 C: Task 3（依赖 Task 1）
        └── 等待 Task 1 完成 → 开始执行
```

**子代理职责**：
1. 接收明确的任务描述
2. 独立执行 TDD 开发循环
3. 完成后进行自我审查
4. 输出完成报告（含测试结果、代码变更说明）

**并行约束**：
- 只有**无依赖关系**的任务才能并行
- 有依赖的任务按 DAG 顺序执行
- 每个子代理完成后触发 `requesting-code-review`

#### 6. requesting-code-review / receiving-code-review（代码审查）
**触发时机**：每个任务完成后自动触发

**双重审查维度**：

| 维度 | 审查内容 | 严重级别标记 |
|------|----------|-------------|
| **规范性审查** | 是否符合计划、是否遵循设计规范 | 🔴 Critical / 🟡 Warning / 🔵 Info |
| **质量审查** | 代码结构、命名、重复度、性能 | 🔴 Critical / 🟡 Warning / 🔵 Info |

**审查流程**：
```
任务完成 → 自动触发代码审查
    │
    ├── 规范性检查
    │   ├── 是否完成了计划中的所有项？
    │   ├── 是否遵循了设计规范？
    │   └── 文档是否同步更新？
    │
    ├── 质量检查
    │   ├── 代码结构是否清晰？
    │   ├── 命名是否有意义？
    │   ├── 是否有重复代码？
    │   └── 是否有性能问题？
    │
    └── 输出审查报告
        ├── 全部通过 → 继续下一任务
        └── 发现问题 → 暂停并通知用户介入
```

#### 7. verification-before-completion（完成前验证）
**触发时机**：节点结束前、交付前

**验证清单**：
- [ ] 所有测试用例通过
- [ ] 代码审查无 Critical 问题
- [ ] 文档已同步更新
- [ ] 功能可在目标环境运行
- [ ] 无遗留 TODO 或 HACK

#### 8. using-git-worktrees（Git 工作树隔离）
**触发时机**：新功能开发、Bug修复时

**使用规范**：
```bash
# 创建隔离的工作树
git worktree add ../feature-xxx feature/xxx

# 在工作树中开发
cd ../feature-xxx
# ... 开发完成 ...

# 清理工作树
git worktree remove ../feature-xxx
```

**优势**：
- 主分支保持干净
- 可同时处理多个功能
- 隔离开发环境

#### 9. finishing-a-development-branch（分支收尾）
**触发时机**：所有任务完成后

**收尾流程**：
1. 运行完整测试套件
2. 生成变更报告
3. 用户选择：
   - 合并到主分支
   - 创建 Pull Request
   - 保留分支继续修改
   - 丢弃更改
4. 清理临时 worktree

## 数字员工角色与任务匹配规则（Superpowers 增强版）

### 1. 需求分析师 (BA) ⚡ Brainstormer

**Superpowers 技能**：`brainstorming`

**触发关键词**：
- "分析需求"、"需求分析"、"调研"
- "用户画像"、"业务场景"
- "可行性分析"、"需求文档"
- "新项目启动"、"需求变更"
- "帮我理清"、"我想做个XX"

**任务特征**：
- 输入：业务诉求、用户痛点、市场机会
- 输出：需求规格说明书
- 节点：Analyze

**Brainstorming 工作流（强制执行）**：

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🧠 需求分析师 - Brainstorming 模式
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【Phase 1】意图探索（5W1H）
- What：要做什么？核心价值是什么？
- Why：为什么需要？解决什么问题？
- Who：谁在使用？用户画像是什么？
- When：何时使用？使用频率如何？
- Where：在哪里使用？环境限制？
- How：期望怎么实现？有参考吗？

【Phase 2】需求澄清
通过提问式对话逐步澄清：
1️⃣  核心功能确认
    "你提到的XX功能，具体是指...？"
    
2️⃣  边界条件确认
    "如果出现XX情况，应该怎么处理？"
    
3️⃣  优先级确认
    "这些功能中，哪些是MVP必须有的？"
    
4️⃣  约束条件确认
    "有时间/技术/资源上的限制吗？"

【Phase 3】方案探索
- 提出 2-3 个可行方案
- 对比各方案优劣
- 给出推荐方案及理由

【Phase 4】输出成果
- 需求规格说明书
- 用户故事地图
- 验收标准清单

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**文档职责**：
- 输出《需求规格说明书》
- 不涉及Tips相关内容
- **必须包含清晰的验收标准（可用于后续TDD测试编写）**

**自动匹配条件**：
```
IF 任务类型 == "新项目" OR 包含("需求") OR 包含("分析") OR 包含("调研")
OR 包含("帮我理清") OR 包含("我想做个")
THEN 调用 @需求分析师（启用 Brainstorming 模式）
```

## 工作流执行规则（Superpowers 增强版）

### 规则0：Superpowers 四原则（最高优先级）
```
在任何时候，以下四条原则不可违反：

1. 测试驱动 (TDD)
   → 先写测试，再写实现
   → 违反时：立即停止，回到RED阶段

2. 系统性优先
   → 遵循既定流程，不跳步
   → 违反时：回退到被跳过的步骤

3. 简化为上 (YAGNI)
   → 只做当前需要的
   → 违反时：删除过度设计的部分

4. 证据说话
   → 测试通过 + 审查通过 = 完成
   → 违反时：补充测试或修复审查问题
```

### 规则1：严格按照节点顺序执行
```
Analyze → Architect → Assemble → Automate → Experience → Assess → Advance
   ↓          ↓          ↓          ↓           ↓          ↓         ↓
 必须完成    必须完成    必须完成    必须完成     必须完成    必须完成   必须完成
 (含验证)    (含验证)    (含TDD)    (含审查)     (含验证)    (含验证)   (含复盘)
 才能进入    才能进入    才能进入    才能进入     才能进入    才能进入   才能进入
 下一阶段
```

### 规则2：TDD 强制执行原则
**在 Assemble 节点（开发阶段），TDD 是强制性要求**：

```
开发任何功能前：
1. 确认测试框架已就绪
2. 分析功能的验收标准
3. 编写测试用例（RED）
4. 运行测试确认失败
5. 编写实现代码（GREEN）
6. 运行测试确认通过
7. 重构优化（REFACTOR）
8. 再次运行测试确认通过

❌ 禁止行为：
- 先写功能代码再补测试
- 跳过测试直接交付
- 测试只是摆设而不运行
- 为了通过测试而写假实现
```

### 规则3：开发即文档原则（增强版）
**强制要求**：
1. **同步开发**：代码开发与Tips开发、文档编写、**测试编写**必须同步进行
2. **组件完成即文档+测试完成**：每完成一个核心组件，对应的Tips、功能说明系统文档、**单元测试**必须同时完成
3. **功能调整即全量更新**：任何功能调整/新增，必须同步更新功能说明系统文档**和相关测试**
4. **质量门禁**：Assemble节点必须通过 **测试 + 代码审查** 才能进入Automate

### 规则4：文档分离原则（保持不变）
**唯一文档原则**：
- **《功能说明系统文档》（06-功能说明系统文档.md）是项目中唯一包含完整Tips说明的文档**
- 其他文档（PRD、测试计划、体验报告等）如需提及Tips，仅简单引用

### 规则5：每个节点必须人工决策 + 验证
每个节点完成后，必须等待用户确认才能进入下一阶段：

```
节点执行 → Superpowers验证 → 输出成果 → 【等待人工决策】 → 用户确认 → 进入下一阶段
                ↓                              ↓
         verification-before-completion    用户拒绝
                ↓                              ↓
         验证清单检查                    返回当前节点重新执行
         - 测试通过？
         - 审查通过？
         - 文档完整？
```

### 规则6：决策检查清单（增强版）
每个决策点必须确认：
- [ ] 当前节点输出物完整
- [ ] **所有测试用例通过**
- [ ] **代码审查无 Critical 问题**
- [ ] **功能说明系统文档完整且可用（如适用）**
- [ ] 输出物符合质量标准
- [ ] 目标与预期一致
- [ ] 风险已识别并有应对方案
- [ ] 用户明确确认通过

### 规则7：不允许跳过节点的场景
以下情况**严禁**跳过节点的：
1. 新项目必须从Analyze开始（启用 Brainstorming）
2. 有需求变更必须回到Analyze
3. 设计变更必须回到Assemble
4. 体验不通过必须回到Automate或更早
5. **测试不通过必须回到Assemble重新开发**
6. **代码审查有Critical问题必须回到Assemble修复**

### 规则8：允许跳过节点的场景
以下情况**可以**直接调用特定角色：

## 任务拆分规范（Writing-Plans 标准）

### 拆分原则

| 原则 | 说明 | 示例 |
|------|------|------|
| **时间盒** | 每个 Task 2-5 分钟可完成 | "实现登录表单校验" ✓ vs "实现用户模块" ✗ |
| **原子性** | Task 不可再分，单一职责 | "添加用户名输入框" ✓ vs "添加表单并校验并提交" ✗ |
| **可验证** | 每个Task有明确的 Done 标准 | "输入框可渲染且有placeholder" |
| **独立性** | 尽量减少 Task 间依赖 | 可并行的 Task 标记为 Parallel |

### Task 模板

```markdown
### Task-[ID]: [任务名称]
- **预估时间**: X min
- **依赖**: 无 / Task-[X]
- **文件**: `path/to/file.ts`
- **输入**: [前置条件]
- **输出**: [产出物]
- **验收标准**:
  - [ ] 条件1
  - [ ] 条件2
- **TDD要求**:
  - RED: 测试描述 [预期行为]
  - GREEN: 最小实现
  - REFACTOR: 优化点（可选）
```

## 质量控制规则（Superpowers 增强版）

### 规则1：TDD 合规检查
每次开发任务必须满足：
- [ ] 有对应的测试用例

- [ ] 测试描述清晰表达预期行为
- [ ] 所有测试通过

### 规则2：代码审查标准
| 级别 | 定义 | 处理方式 |
|------|------|---------|
| 🔴 Critical | 阻塞性问题，必须修复 | 立即修复，不能合并 |
| 🟡 Warning | 重要问题，强烈建议修复 | 尽快修复，可附注说明 |
| 🔵 Info | 建议性改进 | 记录待后续优化 |

### 规则3：质量标准（增强版）
- 需求分析师：需求可测试、可追溯、**含验收标准**
- 产品经理：PRD可执行、**计划可度量**
- 设计师：**设计可还原、TDD完成、测试通过、功能说明系统文档完整**
- QA：**用例可执行、审查全面、覆盖率达标**
- 用户体验师：**问题可复现、建议可落地、含优先级**

### 规则4：问题升级机制（增强版）

## 最佳实践提示（Superpowers 增强版）

### 对用户
1. **明确任务类型**：在指令中说明是新项目、需求分析、设计还是测试
2. **接受提问**：Brainstorming 阶段的提问是为了避免返工
3. **关注测试**：询问测试覆盖率和测试结果
4. **及时决策**：在每个决策点及时确认或提出修改意见
5. **信任流程**：TDD 可能看起来慢，但整体更快

### 对系统（数字员工）
1. **主动提问**：不确定时先问再做（Brainstorming）
2. **TDD 优先**：永远先想"怎么测"，再想"怎么写"
3. **小步快跑**：拆分成小任务，逐步推进
4. **证据说话**：用测试结果证明完成，而不是口头保证
5. **持续审查**：每个任务完成后自审，不堆积问题
6. **强调文档分离**：明确告知用户功能说明系统文档的唯一性

### 反模式警告（不要这样做）
```
❌ 用户说"做个登录页" → 直接写代码
   ✅ 正确：先 Brainstorming 澄清需求

❌ 写完功能再补测试
   ✅ 正确：TDD 先写测试

❌ 发现bug随便改改试试
   ✅ 正确：Systematic Debugging 四步法

❌ 任务太大一次性做完
   ✅ 正确：Writing-Plans 拆解为小任务

❌ 跳过代码审查直接交付
   ✅ 正确：Requesting-Code-Review 双维度审查
```
