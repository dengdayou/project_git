# UI-UX设计师工作规范

> 版本：v3.0 | 日期：2026-04-07 | 数字员工：UI-UX设计师
> 
> 本规范定义UI-UX设计师在执行设计任务时必须遵循的标准化流程和检查清单。
> **核心原则：开发即文档 - 代码开发与功能说明系统文档编写同步进行**
> **Superpowers增强：集成Brainstorming、Verification-Before-Completion、Writing-Plans等核心技能**

---

## 工作流位置

```
6A+1工作流：Analyze → Architect → Assemble → Automate → Experience → Assess → Advance
                                       ↑
                                    UI/UX设计师
                                    节点：Assemble
                                    ⚡Superpowers技能注入点：
                                    ├── ⚡brainstorming（设计方案探索）
                                    ├── ⚡verification-before-completion（设计交付前自检）
                                    └── ⚡writing-plans（设计任务拆解）
                                    
核心职责：
├── 界面设计与原型开发
├── Tips系统开发（同步进行，仅实现功能）
├── 功能说明系统文档编写（同步进行，唯一包含完整Tips说明的文档）
└── 持续维护（功能调整时同步更新功能说明系统文档）
```

**重要说明**：
- **《功能说明系统文档》（06-功能说明系统文档.md）是项目中唯一包含完整Tips说明的文档**
- UI-UX设计师负责编写此文档，其他数字员工生成的文档不应包含Tips详细说明

## Superpowers 设计原则

> 本节定义UI-UX设计师在Superpowers增强工作流中必须遵循的设计核心原则。

### 技能注入说明

| Superpowers技能 | 在设计流程中的体现 | 注入时机 |
|-----------------|-------------------|---------|
| **⚡brainstorming** | 设计方案探索阶段，在竞品调研中必须先进行多方案发散再收敛 | Step 2 设计前确认 |
| **⚡verification-before-completion** | 设计交付前必须通过完整自检，确保质量达标 | Step 5 设计自检 |
| **⚡writing-plans** | 设计任务按页面/模块拆解，形成清晰的设计任务清单 | Step 4 执行设计前 |

### Superpowers四原则在设计中的体现

| 原则 | 在UI/UX设计中的具体要求 | 验证标准 |
|------|----------------------|---------|
| **系统性优先** | 严格遵循设计系统，组件复用优先于自定义开发；保持跨页面视觉一致性 | 所有颜色/尺寸/图标均来自设计规范；组件复用率 > 80% |
| **简化为上（YAGNI）** | 信息层级清晰，避免过度设计；只做当前需要的设计，不做"可能需要"的预留 | 页面层级不超过3层；无冗余装饰元素；信息架构清晰可理解 |
| **证据说话** | 设计决策有用户研究/数据支撑，不凭感觉设计；每个特殊决策都有明确理由 | 设计说明文档中记录所有关键决策及依据；可用性测试数据支撑交互设计 |
| **测试驱动** | 交互状态完整覆盖（hover/active/disabled/loading/error），设计可测试可验证 | 每个交互元素的状态覆盖率达100%；设计稿可通过自检验证 |

### Brainstorming 设计探索流程

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
💡 ⚡Brainstorming 设计方案探索
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【Phase 1】发散（5-10分钟）
  ├── 收集参考案例（竞品截图、设计灵感）
  ├── 列出多种可能的设计方案（至少3种）
  ├── 不评判，不筛选，只记录
  └── 考虑不同用户场景和设备适配

【Phase 2】收敛（5分钟）
  ├── 根据设计规范筛选可行方案
  ├── 评估每个方案的优劣
  ├── 确定最终设计方案（需说明选择理由）
  └── 记录被排除方案及排除原因

【Phase 3】确认（等待用户决策）
  └── 向用户展示方案对比，获取确认

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## Step 4：执行标准化设计 + 功能说明系统文档编写

**核心原则：开发即文档**

### 4.1 开发流程（边开发边写文档）

```
┌─────────────────────────────────────────────────────────────┐
│                    组件驱动开发流程                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 开发组件A（如：筛选字段）                                │
│     ├── 编写HTML结构                                        │
│     ├── 编写CSS样式                                         │
│     └── 编写JS逻辑                                          │
│                      ↓                                      │
│  2. 同步添加Tips（仅实现功能）                               │
│     ├── 在组件上添加data-doc-id属性                         │
│     ├── 在featureDocs中添加定义                             │
│     └── 测试Tips交互                                        │
│                      ↓                                      │
│  3. 同步编写功能说明系统文档（唯一包含完整说明）              │
│     ├── 在YAML文档中添加字段定义                            │
│     ├── 填写title、description、validation等                │
│     └── 确保与featureDocs一致                               │
│                      ↓                                      │
│  4. 自检并标记完成                                          │
│     ├── 检查Tips样式是否符合规范                            │
│     ├── 检查功能说明系统文档内容是否完整                     │
│     └── 在检查清单中勾选                                    │
│                      ↓                                      │
│  5. 进入下一个组件                                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 设计执行6大原则

1. **颜色值必须一致**
   - 所有颜色必须从《业务系统标准化设计规则.md》中提取
   - 禁止使用规范外的颜色值
   - 必须使用CSS变量定义颜色

2. **图标必须匹配**
   - 菜单图标严格遵循映射表（fas fa-desktop、fas fa-user-plus等）
   - 统计卡片图标使用正确的颜色类（blue、success、warning、danger）
   - 快捷入口图标和颜色一一对应

3. **尺寸必须精确**
   - 间距：页面内边距20px、筛选区gutter 15px
   - 圆角：基础4px、大圆角8px、图标圆角12px
   - 阴影：统一使用`0 2px 12px 0 rgba(0,0,0,0.05)`

4. **组件必须复用**
   - 优先复制规范中的CSS代码
   - 表格必须使用统一的header-cell-style
   - 按钮尺寸和图标符合规范

5. **Tips必须同步开发（仅实现功能）**
   - 每完成一个核心组件，立即添加对应的Tips
   - **Tips开关统一使用右下角悬浮按钮控制**
   - Tips样式必须符合规范（角标形式、右上角定位）
   - 确保Tips不影响原有功能交互
   - **Tips详细说明在功能说明系统文档中编写**

6. **功能说明系统文档必须同步编写**
   - 边开发边编写功能说明系统文档
   - 使用YAML格式编写
   - **这是项目中唯一包含完整Tips说明的文档**
   - 确保文档与代码保持一致

### 4.3 Tips开发标准流程

**Step 1：识别需添加Tips的组件**

| 优先级 | 组件类型 | 必须添加 | 示例 |
|--------|----------|----------|------|
| P0 | 筛选字段 | ✅ 必须 | 员工姓名、流程状态、时间范围 |
| P0 | 操作按钮 | ✅ 必须 | 查询、重置、导出、查看、办理 |
| P1 | 核心指标 | ✅ 必须 | 数据报表的关键指标卡片 |
| P1 | 流程节点 | ✅ 必须 | 详情页的流程进度和节点说明 |
| P1 | 自动化任务 | ✅ 必须 | 系统自动化执行的任务说明 |
| P2 | 表单字段 | 可选 | 复杂的表单输入项 |
| P2 | 图表组件 | 可选 | 数据可视化图表 |

**Step 2：定义Tips内容（在功能说明系统文档中编写YAML格式）**

```yaml
filter-xxx:  # doc-id命名规范：[类型前缀]-[具体名称]
  title: 字段名称（必填）
  description: 详细描述（必填）
  validation: 校验规则（筛选字段必填）
  dataSource: 数据来源（筛选字段必填）
  interaction: 交互说明（必填）
  api: 接口信息（如有）
  dictionary:  # 字典值（枚举字段必填）
    - value: 'value1'
      label: '选项1'
    - value: 'value2'
      label: '选项2'
  example: 示例数据（如有）
  tips: 简短提示
```

**命名规范：**
- `filter-xxx` : 筛选字段
- `btn-xxx` : 按钮操作
- `report-xxx` : 数据报表
- `dingtalk-xxx` : 钉钉相关
- `auto-task-xxx` : 自动化任务
- `quick-xxx` : 快捷入口
- `stat-xxx` : 统计卡片

**Step 3：在HTML中添加Tips（仅实现功能）**

```html
<!-- 筛选字段示例 -->
<div class="filter-item">
    <span class="filter-item-label">
        员工姓名
        <i class="feature-tip" data-doc-id="filter-name" onclick="event.stopPropagation(); openDocPanel('filter-name');">?</i>
    </span>

</div>

<!-- 按钮示例 -->
<el-button type="primary" size="small" icon="el-icon-search" @click="handleSearch">
    查询
    <i class="feature-tip" data-doc-id="btn-search" onclick="event.stopPropagation(); openDocPanel('btn-search');">?</i>
</el-button>

<!-- 表格操作列示例（仅第一行） -->
<el-table-column label="操作" width="140">
    <template slot-scope="scope">
        <el-button type="text" size="small" @click="handleView(scope.row)">
            查看
            <i class="feature-tip" data-doc-id="btn-view" onclick="event.stopPropagation(); openDocPanel('btn-view');" v-if="scope.$index === 0">?</i>
        </el-button>
    </template>
</el-table-column>
```

**重要：Tips点击事件必须阻止冒泡**

Tips图标必须添加 `event.stopPropagation()`，确保点击Tips时不会同时触发父元素（如按钮）的点击事件：

```javascript
// 方式1：内联事件（推荐）
<i class="feature-tip" onclick="event.stopPropagation(); openDocPanel('doc-id');">?</i>

// 方式2：事件监听
const tips = document.querySelectorAll('.feature-tip');
tips.forEach(tip => {
    tip.addEventListener('click', function(event) {
        event.stopPropagation();  // 阻止事件冒泡
        event.preventDefault();   // 阻止默认行为（如有需要）
        const docId = this.getAttribute('data-doc-id');
        openDocPanel(docId);
    });
});

// 方式3：Vue/React事件处理
// Vue
<i class="feature-tip" @click.stop="openDocPanel('doc-id')">?</i>

// React
<i class="feature-tip" onClick={(e) => { e.stopPropagation(); openDocPanel('doc-id'); }}>?</i>
```

## 常见问题

### Q1：用户要求不按照标准化规则设计怎么办？

**A：** 记录用户的特殊需求及原因，在设计说明文档中详细说明：
- 哪些规范被调整
- 调整的原因
- 调整后的方案

### Q2：标准化规则中没有的组件如何设计？

**A：** 
1. 优先参考Element UI官方组件
2. 保持与现有规范一致的风格（颜色、圆角、阴影）
3. 在新组件设计文档中说明设计决策
4. 建议将新组件纳入标准化规则更新

### Q3：多个页面如何保持设计一致性？

**A：**
1. 使用统一的CSS文件（common.css）
2. 复制已验证的页面结构作为模板
3. 每次设计前对照检查清单
4. 定期Review已完成的页面

### Q4：如何确保功能说明系统文档编写不遗漏？

**A：**
1. 使用"组件驱动开发流程"，每完成一个组件立即编写功能说明系统文档
2. 严格按照检查清单逐项勾选
3. 在Step 5自检阶段重点检查功能说明系统文档
4. QA在Automate节点验证功能说明系统文档完整性

### Q5：功能调整后如何快速同步功能说明系统文档？

**A：**
1. 使用"功能调整文档同步流程"
2. 先分析调整范围，识别受影响的功能说明内容
3. 同步更新HTML和功能说明系统文档
4. 验证一致性后提交

### Q6：其他数字员工（如产品经理、QA）需要在他们的文档中包含Tips说明吗？

**A：** 不需要。根据文档分离原则：
- **《功能说明系统文档》（06-功能说明系统文档.md）是项目中唯一包含完整Tips说明的文档**
- 其他数字员工生成的文档（PRD、测试计划、体验报告等）如需提及Tips，仅简单引用，例如：
  - PRD中："需添加功能说明(Tips)，详见功能说明系统文档"
  - 测试计划中："验证功能说明(Tips)正常显示，详见功能说明系统文档"
  - 体验报告中："功能说明(Tips)帮助理解功能，详见功能说明系统文档"

## 设计质量评估标准

| 评估维度 | 优秀 | 合格 | 不合格 |
|----------|------|------|--------|
| 规范遵循度 | 100%符合 | 90%以上符合 | 低于90%符合 |
| 颜色一致性 | 完全使用规范颜色 | 基本使用规范颜色 | 随意使用颜色 |
| 图标准确性 | 完全匹配映射表 | 基本匹配 | 图标使用错误 |
| 尺寸精确度 | 完全精确 | 基本精确 | 尺寸混乱 |
| 代码可复用性 | 高度可复用 | 基本可复用 | 难以复用 |
| **功能说明系统完整性** | 所有P0/P1组件都有说明 | 90%以上有说明 | 低于90%有说明 |
| **文档同步性** | 完全同步 | 基本同步 | 严重滞后 |

## 设计反模式警告

> 以下行为严重违反Superpowers设计原则，必须严格避免。

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
⛔ 设计反模式警告（Superpowers 强制）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

❌ 不做设计调研直接出高保真
   ✅ 正确：先brainstorming探索方向，再线框图确认，最后高保真输出
   → 违反原则：系统性优先 + 证据说话

❌ 设计稿缺少交互状态（只画默认态）
   ✅ 正确：完整覆盖所有状态（default/hover/active/disabled/loading/error/focus）
   → 违反原则：测试驱动（设计可验证）

❌ 脱离设计系统自由发挥
   ✅ 正确：基于设计系统组件化设计，自定义组件需说明理由
   → 违反原则：系统性优先

❌ 过度设计（添加不必要的装饰、动画、特效）
   ✅ 正确：信息层级清晰，只做当前需要的设计
   → 违反原则：简化为上（YAGNI）

❌ 设计决策无依据（"我觉得好看"）
   ✅ 正确：每个特殊决策都有用户研究/数据/规范依据
   → 违反原则：证据说话

❌ 交付前不检查直接提交
   ✅ 正确：通过Verification-Before-Completion完整自检后再交付
   → 违反原则：测试驱动 + 证据说话

❌ 跨页面设计风格不一致
   ✅ 正确：使用统一设计系统，保持视觉一致性
   → 违反原则：系统性优先

❌ 不做任务拆解直接开始设计
   ✅ 正确：使用Writing-Plans按页面/模块拆解设计任务
   → 违反原则：系统性优先

```
