# 功能说明系统实施规范（项目规则）

> 版本：v3.0 | 日期：2026-04-07 | 适用范围：SHR行政人力系统所有功能模块
> 
> 本规范定义了功能说明系统（Feature Tips System）的标准实施流程，确保所有功能模块的一致性和可维护性。
> **核心原则：开发即文档，持续维护，完成前验证**
> **Superpowers 增强：集成 verification-before-completion 机制，确保 Tips 功能在验收阶段通过完整验证**

---

## 一、规范概述

### 1.1 目的
- 统一功能说明系统的实施标准
- 提高原型交付质量，便于开发人员理解
- 降低后续功能迭代的学习成本
- 确保设计规范和代码实现的一致性
- **确保功能调整/新增时文档同步更新**
- **确保 Tips 功能在交付前通过系统性验证（Superpowers verification-before-completion）**

### 1.2 适用范围
- 所有新增功能模块
- 所有功能迭代优化
- 所有页面重构
- 所有原型交付
- **所有功能调整/更新**
- **所有 Tips 功能的验收验证环节**

### 1.3 核心原则
1. **完整性**：所有核心组件必须有对应的tips说明
2. **一致性**：相同类型的组件使用相同的tips样式和交互
3. **可维护性**：tips定义集中管理，便于统一更新
4. **零侵入**：tips系统不影响原有功能和交互
5. **开发即文档**：代码开发与Tips开发、文档编写同步进行
6. **持续维护**：功能调整/新增时，同步更新相关Tips和文档
7. **完成前验证**：Tips功能必须在验收阶段通过完整验证，验证维度涵盖完整性、一致性、功能性、可维护性，未通过验证不得视为完成

## 三、实施流程（必做步骤）

### 3.1 设计阶段（Assemble节点）

#### 步骤1：识别需要添加tips的组件

**必须添加tips的组件类型：**

| 组件类型 | 优先级 | 说明 | 示例 |
|---------|--------|------|------|
| 筛选字段 | P0 | 所有列表页的筛选条件 | 员工姓名、流程状态、时间范围 |
| 操作按钮 | P0 | 查询、重置、导出、查看、办理等 | 查询按钮、导出按钮、查看按钮 |
| 核心指标 | P1 | 数据报表的关键指标卡片 | 待入职人数、本月入职率 |
| 流程节点 | P1 | 详情页的流程进度和节点说明 | 审批节点、自动化任务节点 |
| 自动化任务 | P1 | 系统自动化执行的任务说明 | 账号创建、权限分配 |
| 钉钉审批 | P1 | 钉钉集成的相关信息 | 钉钉审批状态、审批人 |

**可选添加tips的组件类型：**

| 组件类型 | 优先级 | 说明 |
|---------|--------|------|
| 表单字段 | P2 | 复杂的表单输入项 |
| 图表组件 | P2 | 数据可视化图表 |
| 统计卡片 | P2 | 工作台的数据概览 |

#### 步骤2：定义tips内容

**每个tips必须包含的字段：**

```yaml
[doc-id]:
  title: 组件名称（必填）
  description: 详细描述（必填）
  validation: 校验规则（筛选字段必填）
  dataSource: 数据来源（筛选字段必填）
  interaction: 交互说明（必填）
  api: 接口信息（如有）
  dictionary: 字典值（枚举字段必填）
  example: 示例数据（如有）
```

**命名规范：**

```
[类型前缀]-[具体名称]

示例：
- filter-name          # 筛选字段-员工姓名
- filter-process-no    # 筛选字段-流程编号
- btn-search           # 按钮-查询
- btn-view             # 按钮-查看
- report-overview      # 报表-综合概览
- dingtalk-approval    # 钉钉审批
- auto-task-account    # 自动化任务-账号创建
- quick-entry          # 快捷入口
- stat-card            # 统计卡片
```

## Superpowers 完成前验证（Verification-Before-Completion）

> 本节基于 Superpowers `verification-before-completion` 技能，为 Tips 功能定义系统化的完成前验证标准。
> Tips 功能未通过本节全部验证项，不得视为开发完成。

### 验证原则

Tips 功能的验证遵循 **证据优于声明** 原则——每项验证必须通过实际操作确认，而非仅凭开发者声明。

### Tips系统专属验证清单

#### 维度一：完整性验证

| 验证项 | 验证方式 | 通过标准 |
|--------|----------|----------|
| P0组件Tips覆盖率 | 逐页检查所有P0优先级组件 | 100%覆盖，无遗漏 |
| P1组件Tips覆盖率 | 逐页检查所有P1优先级组件 | 100%覆盖，无遗漏 |
| Tips必填字段完整性 | 逐条检查featureDocs对象 | title、description、interaction三个必填字段无空值 |
| YAML文档字段完整性 | 逐条检查YAML文档 | 与featureDocs必填字段一致 |
| 更新记录完整性 | 检查文档更新记录 | 每次变更均有对应记录 |

#### 维度二：一致性验证

| 验证项 | 验证方式 | 通过标准 |
|--------|----------|----------|
| featureDocs与YAML文档一致性 | 交叉比对doc-id和字段值 | 所有doc-id完全匹配，字段内容完全一致 |
| HTML data-doc-id与featureDocs一致性 | 检查所有带data-doc-id的元素 | 每个data-doc-id在featureDocs中均有定义 |
| Tips样式一致性 | 视觉检查各页面Tips样式 | 同类型组件Tips尺寸、颜色、位置一致 |
| 版本号一致性 | 检查文档头部与更新记录 | 版本号与最新记录匹配 |
| PRD需求与Tips内容一致性 | 对照PRD文档逐条核实 | Tips描述与PRD中的功能定义一致 |

#### 维度三：功能性验证

| 验证项 | 验证方式 | 通过标准 |
|--------|----------|----------|
| 悬浮按钮开关功能 | 点击悬浮按钮 | 可正常切换Tips显示/隐藏状态 |
| 状态持久化 | 开启/关闭后刷新页面 | 状态保持不变 |
| Tips点击事件独立性 | 点击Tips图标 | 不触发所属按钮的点击事件 |
| 文档面板内容展示 | 点击不同Tips图标 | 面板显示对应doc-id的正确内容 |
| 面板关闭功能 | 关闭文档面板 | 面板正常关闭，不影响页面状态 |
| 表格Tips仅首行显示 | 检查表格多行数据 | 仅第一行操作按钮显示Tips图标 |
| 弹窗内Tips受控 | 打开弹窗后切换Tips开关 | 弹窗内Tips随开关状态变化 |
| 快捷键冲突检测 | 在页面中使用各快捷键 | Tips功能不影响页面原有快捷键 |

#### 维度四：可维护性验证

| 验证项 | 验证方式 | 通过标准 |
|--------|----------|----------|
| 命名规范合规性 | 检查所有doc-id命名 | 符合 `[类型前缀]-[具体名称]` 规范 |
| 代码组织清晰度 | 检查featureDocs对象结构 | 按模块/页面分组，有注释说明 |
| 文档结构清晰度 | 检查YAML文档结构 | 按组件类型分章节，结构清晰 |
| CSS样式集中管理 | 检查Tips相关CSS | 所有Tips样式集中在统一位置，无散落内联样式 |

### 与QA verification-before-completion 的协同关系

```
┌─────────────────────────────────────────────────────────────┐
│          verification-before-completion 协同验证流程         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  开发者自验证（Assemble节点完成时）                          │
│  ├── 完成维度一：完整性验证                                  │
│  ├── 完成维度二：一致性验证                                  │
│  ├── 完成维度三：功能性验证                                  │
│  ├── 完成维度四：可维护性验证                                │
│  └── 确认全部通过 → 提交QA                                  │
│                      ↓                                      │
│  QA独立验证（Automate节点）                                  │
│  ├── 独立执行四维度验证（不依赖开发者声明）                   │
│  ├── 交叉验证：PRD ↔ Tips内容 ↔ featureDocs ↔ YAML文档      │
│  ├── 回归验证：确认Tips不影响已有功能                        │
│  └── 输出验证报告                                           │
│                      ↓                                      │
│  验证结果判定                                               │
│  ├── 全部通过 → 进入Assess节点                              │
│  ├── 存在Critical问题 → 返回Assemble节点修复                │
│  └── 存在Minor问题 → 记录问题，进入Assess节点附带说明        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**协同原则：**
- 开发者在 Assemble 节点完成自验证后才能提交 QA
- QA 在 Automate 节点进行独立验证，不依赖开发者的验证结果
- 任何 Critical 级别问题必须返回 Assemble 节点修复
- 验证报告作为 Automate 节点的标准输出物

## 八、常见问题（FAQ）

### Q1：哪些组件必须添加tips？
**A：** 所有筛选字段、操作按钮、核心指标、流程节点、自动化任务、钉钉审批信息都必须添加tips。

### Q2：表格操作列的tips为什么只显示在第一行？
**A：** 为了避免列表过于杂乱，仅第一行显示tips作为示例即可。已通过CSS控制：`.el-table__row:not(:first-child) .el-button .feature-tip { display: none !important; }`

### Q3：点击tips会触发按钮点击吗？
**A：** 不会。已通过JavaScript事件拦截处理，使用`stopPropagation()`、`preventDefault()`、`stopImmediatePropagation()`三重保障。

### Q4：tips的状态会保存吗？
**A：** 会。使用localStorage保存用户选择，刷新页面后保持状态。

### Q5：如何快速为新功能添加tips？
**A：** 按照"实施流程"章节的5个步骤执行：识别组件 → 定义内容 → 更新文档 → 更新代码 → 添加属性 → 验收验证。

### Q6：文档和代码必须保持一致吗？
**A：** 是的。文档用于查阅和维护，代码用于实际运行，两者必须保持一致。建议先更新文档，再更新代码。

### Q7：功能调整后如何确保文档同步更新？
**A：** 使用"功能调整文档同步流程"：分析调整范围 → 同步更新HTML → 同步更新文档 → 验证一致性 → 完成确认。

### Q8：如何避免遗漏Tips开发？
**A：** 
1. 使用"组件驱动开发流程"，每完成一个组件立即添加Tips
2. 严格按照检查清单逐项勾选
3. QA在Automate节点进行Tips完整性检查
4. 定期Review补充缺失的Tips

### Q9：什么是 verification-before-completion 验证？
**A：** 这是 Superpowers 核心技能之一，要求 Tips 功能在交付前必须通过四个维度的系统化验证：完整性、一致性、功能性、可维护性。开发者先自验证，QA 再独立验证，全部通过后才视为完成。

### Q10：Tips 开发应该什么时候进行？
**A：** Tips 开发必须与功能开发同步进行，而不是在功能开发完成后补加。这是"开发即文档"原则的具体体现，也是 Superpowers 系统性优于临时方案原则的要求。

### 9.4 反模式警告

以下做法违反 Superpowers 核心原则，必须避免：

**反模式1：事后补Tips**
```
X  开发完功能后再补Tips
   正确做法：开发功能与Tips开发同步进行
```

**反模式2：Tips内容脱离PRD**
```
X  Tips内容与PRD需求不一致
   正确做法：Tips内容基于PRD需求定义，变更时同步更新
```

**反模式3：文档与代码脱节**
```
X  文档和代码不同步更新
   正确做法：功能调整时文档代码同步更新
```

**反模式4：跳过验证直接交付**
```
X  不做 verification-before-completion 验证就视为完成
   正确做法：必须通过四维度验证（完整性、一致性、功能性、可维护性）后才视为完成
```

**反模式5：仅靠声明不靠证据**
```
X  开发者声称Tips已完成但无验证证据
   正确做法：QA独立执行验证，验证报告作为交付物
